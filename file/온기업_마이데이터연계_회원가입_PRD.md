# 캠코 온기업(ON-KIUP) 차세대 프로젝트
## 기업/투자자 회원 마이데이터·행정망 연계 가입 간소화 PRD

> 작성: UI/UX 디렉터 관점 검토안 | KRDS(행정안전부 범정부 UI/UX 디자인시스템) '신청' 및 '입력폼' 패턴 준수
> 근거 문서: KRDS 서비스패턴-신청(service_04_01), 기본패턴-입력폼(global_08), 기본패턴-동의(global_03), 기본패턴-개인식별정보입력(global_01)

---

## 0. Why — 이 과제를 하는 이유

현재 온기업 가입 프로세스의 구조적 문제는 단순 "화면이 복잡하다"가 아니라 **사용자가 이미 보유한 진위 확인된 데이터를, 시스템이 신뢰하지 못해 수기로 다시 입력시키는 구조**에 있습니다. 사업자등록번호, 법인등기 정보, 대표자 신원 정보는 이미 국세청·법원행정처·정부24가 진위를 보증하는 데이터입니다. 이를 다시 타이핑하게 만드는 순간, 이탈은 필연적으로 발생합니다.

- **비즈니스 근거**: 캠코의 정책자금·보증·투자연계 사업 특성상 가입자의 상당수는 '급하게 자금이 필요한 소상공인/스타트업 대표'입니다. 가입 단계 이탈률 1%p는 곧 정책금융 접근성 저하로 직결되는 공공기관 KPI 이슈입니다. 이는 단순 전환율(CVR) 문제가 아니라 **정책 수혜자 도달률(Reach)** 문제로 보고되어야 합니다.
- **사용자 행동 근거**: 유사 공공 신청 서비스(홈택스, 정부24, 국민신문고)의 공통 이탈 지점은 '본인확인 이후 서류 제출' 구간입니다. 서류를 파일로 준비해 업로드하는 행위 자체가 이탈 트리거이므로, 여기를 API 자동조회로 대체하는 것이 이번 설계의 핵심 가설입니다.

> **디렉터 관점 질문 1**: 지금 이 프로젝트의 성공 지표를 '가입완료율'로만 잡을 것인가, 아니면 '가입완료까지 걸린 사용자 액션 수(taps/keystrokes)'처럼 더 선행 지표(leading indicator)로 잡을 것인가? 후자가 원인 진단에는 더 유용합니다.

## 1. 서비스 개요 및 목적

| 항목 | 내용 |
|---|---|
| 서비스명 | 캠코 온기업(ON-KIUP) 차세대 – 마이데이터 연계 간편가입 |
| 배경 | 기존 회원가입은 사업자등록증 사본 업로드, 재무정보 수기입력 등 문서 기반(Document-based) 구조 → 심사 지연 및 위변조 리스크 상존 |
| 핵심 목표 | ① 공공 마이데이터(개인) + 행정정보 공동이용망(법인·행정) 연계를 통한 **무서류(Zero-document) 가입** 실현 ② 진위확인 데이터 기반 자동 심사 사전판별로 반려율 감소 |
| 연계 대상 시스템 | 국세청 홈택스(사업자등록상태 진위확인 API), 행정정보 공동이용시스템(정부24 – 법인등기부등본, 사업자등록증명원 등), 공공 마이데이터 종합포털(개인 인증정보, 국세완납증명, 4대보험 가입이력), 금융결제원(계좌실명 확인) |
| 비즈니스 목표 지표 | 가입 완료 소요시간(TTC), 서류 재제출로 인한 심사 반려율, 본인인증 이후 이탈률(Drop-off) |

## 2. 타깃 유저 및 핵심 가치 (유저 시나리오)

### 2-1. 유저 정의 및 사용 환경
- **주 사용자**: ① 법인/개인사업자 대표 또는 재무 담당자(데스크톱 비중 高, 업무시간 내 접속) ② 개인 투자자 회원(반응형/모바일 비중 高, 퇴근 후 접속 집중)
- **환경 특성**: 법인 담당자는 회사 PC(보안 프로그램 설치 환경 다수, 팝업 차단 이슈 존재)에서 접속하는 경우가 많아 **본인인증 수단(공동인증서/PASS)의 새 창(팝업) 의존도를 낮추는 설계**가 필요합니다. 투자자 회원은 모바일 반응형 환경에서 PASS 앱 전환(App-to-App) 흐름이 매끄러워야 합니다.

### 2-2. 핵심 유저 시나리오
> "정책자금 마감이 임박한 소상공인 대표가, 퇴근 전 10분 안에 가입을 마치고 신청서까지 넣고 싶어한다."

1. 사업자등록번호만 입력하면 국세청 API로 상태(계속사업자/휴폐업)를 즉시 검증받는다.
2. PASS 인증 한 번으로 대표자 본인확인과 마이데이터 전송요구가 동시에 처리된다.
3. 법인등기부등본, 사업자등록증명원은 별도 스캔/업로드 없이 화면에 자동으로 채워져 "확인"만 누르면 된다.
4. 시스템이 자동으로 채우지 못하는 최소 항목(담당자 연락처, 정산계좌 등)만 직접 입력한다.

> **글로벌 벤치마킹**: Stripe Atlas/Connect의 KYB(Know Your Business) 플로우는 사업자번호 하나로 국가별 등록기관 API를 조회해 폼을 사전 채움(pre-fill)하는 방식을 취합니다. 국내에서는 토스뱅크 사업자 가입이 홈택스 사업자등록 상태조회 API를 1뎁스 진입 직후 호출해 '휴폐업 사업자'를 조기 컷오프하는 구조를 취하고 있어, 본 설계의 1단계 이탈 방지 벤치마크로 참고할 수 있습니다.

## 3. 핵심 정보 구조(IA) 및 메뉴 트리

### 3-1. GNB/LNB 구조
```
GNB: 온기업 홈 / 사업안내 / 신청하기 / 마이페이지 / 고객센터
└ 회원가입(LNB 없음, 전용 Flow 레이아웃 – 신청형 서비스 패턴 적용)
   ├ [0] 회원유형 선택
   ├ [1] 본인/기업 인증
   ├ [2] 정보 연계 동의(마이데이터/행정정보 공동이용)
   ├ [3] 행정정보 자동조회 및 확인
   ├ [4] 부가정보 입력(필수 최소값)
   ├ [5] 최종 확인 및 제출
   └ [6] 가입/심사 결과 확인
```

### 3-2. 주요 데이터 개체 및 관계 구조
```
[회원(Member)] 1 --- 1 [기업(Corporation)]
[회원(Member)] 1 --- N [본인인증이력(AuthLog)]
[기업(Corporation)] 1 --- N [행정정보스냅샷(AdminDataSnapshot: 사업자등록증명원/법인등기부등본)]
[회원(Member)] 1 --- N [마이데이터전송이력(MyDataConsentLog)]
[회원(Member)] 1 --- 1 [정산계좌(SettlementAccount)]
[회원(Member)] 1 --- 1 [가입심사상태(ApplicationStatus: 접수/자동검증중/서류보완요청/승인/반려)]
```

- **데이터 상태 설계의 핵심 판단**: 행정정보 API로 가져온 값(법인명, 대표자명, 자본금 등)은 **읽기전용(Read-only) 필드**로 고정하고, 사용자가 임의 수정하지 못하게 해야 합니다. 이는 KRDS 개인식별정보 입력 가이드의 "사용자가 잘못 입력한 값을 자동으로 삭제하지 않는다"는 원칙과는 별개로, 오히려 **진위확인 데이터의 무결성 보장**이 더 상위 원칙이 되는 지점입니다. 값이 실제와 다르면 정정은 원본 기관(국세청/법원)에서 하도록 안내하고, 온기업 내에서는 "정보가 다른가요? 정정 방법 안내" 링크(맥락적 도움말 컴포넌트)로 처리합니다.

## 4. 상세 기능 명세 (화면별 요구사항 및 정책)

### 화면 0 — 회원유형 선택 `/signup/type`

- **기능 요약**: 법인/개인사업자 vs 개인투자자 분기. 이후 전체 Flow의 필수 데이터셋이 달라지므로 최초 분기가 중요.
- **User Flow**: 진입 → 카드형 선택(법인·개인사업자 / 개인투자자) → 선택 즉시 다음 단계 자동 진행(별도 확인 버튼 없이, 클릭 자체가 확정 액션)
- **CRUD**: Create(가입세션 생성, TTL 30분) / Read(이전 임시저장 세션 존재 시 "이어하기" 배너 노출)
- **정책**: 세션 미들웨어에서 이미 가입된 사업자번호로 재진입 시 즉시 안내 모달(확인 패턴)로 로그인 유도, 신규 세션 생성 차단

### 화면 1 — 본인/기업 인증 `/signup/verify`

- **기능 요약**: PASS 간편인증 또는 공동/금융인증서로 대표자 본인확인 + 사업자등록번호 진위확인(홈택스 API) 동시 처리
- **User Flow**:
  1. 사업자등록번호 10자리 입력 (하이픈 자동 포맷, Keyup 시 클라이언트 검증)
  2. "사업자 상태 확인하기" 버튼 → 홈택스 API 호출 → 인라인 결과 배지(계속사업자/휴업자/폐업자)
  3. 휴폐업자인 경우 즉시 진행 차단 + 사유 안내 + 고객센터 연결 (신청 플로 1단계의 조기 컷오프)
  4. 계속사업자 확인 시 대표자 본인인증(PASS/인증서) 진행 → App-to-App 전환(모바일) / QR 또는 새 창(데스크톱)
- **CRUD**: Create(AuthLog), Read(홈택스 진위확인 API 응답), Update(가입세션에 인증결과 바인딩)
- **예외 처리**: 인증서 만료, PASS 미가입, 대표자-사업자번호 불일치(대리인 시도) 각각 별도 오류 메시지 분기 — 서버측 검증 실패 시 오류 발생 첫 항목으로 포커스 강제 이동(KRDS 접근성 가이드 준수)

### 화면 2 — 정보 연계 동의 `/signup/consent`

- **기능 요약**: 마이데이터 전송요구 동의 + 행정정보 공동이용 조회 동의를 분리하여 수집
- **User Flow**: 전체 동의 체크박스 상단 배치 → 하위 개별 항목([필수] 개인정보 수집이용, [필수] 행정정보 공동이용 조회, [필수] 마이데이터 전송요구, [선택] 마케팅 활용) → 약관 본문은 디스클로저(Disclosure)로 기본 접힘 상태
- **CRUD**: Create(MyDataConsentLog, 동의 항목별 타임스탬프 개별 저장 — 추후 마이데이터 이용 표준약관상 감사(audit) 요건)
- **정책/예외**: 개별 항목 중 하나라도 '동의 안함'이면 일괄동의 체크박스는 자동 해제 상태 유지(KRDS 동의 패턴 상호작용 가이드). 필수 동의 미이행 시 다음 단계 진입 버튼 비활성화(disabled) 유지.

### 화면 3 — 행정정보 자동조회 및 확인 `/signup/auto-fill`

- **기능 요약**: 이 화면이 전체 설계의 핵심 차별점 — 사용자는 입력하지 않고 "확인"만 함
- **User Flow**:
  1. 로딩 스피너("행정정보를 조회하고 있습니다" + 예상 소요시간 안내)
  2. 조회 완료 후 카드형 레이아웃으로 법인등기부등본 요약(법인명/대표자/자본금/본점소재지), 사업자등록증명원 요약(업태/종목/개업일) 표시 — 모두 읽기전용
  3. 각 카드 하단에 "원문 보기"(모달, 발급원본 PDF 프리뷰) 제공
  4. 정보 불일치 시 "정보가 다른가요?" 도움 링크 → 정정 절차 안내(관할기관 링크, 서비스 내 직접 수정 불가 명시)
- **CRUD**: Create(AdminDataSnapshot – 조회 시점 스냅샷 저장, 이후 변경 이력 추적용) / Read(정부24 행정정보 공동이용 API)
- **예외 처리**: API 응답 지연(타임아웃 8초 초과) 시 "잠시 후 다시 시도" + 수동 서류 업로드 대체 경로 제공(Fallback) — **공공 API 가용성에 100% 의존하지 않는 것이 설계 원칙**

> **디렉터 관점 질문 2**: 행정정보 공동이용 API가 응답 실패했을 때의 Fallback을 '서류 업로드'로 둘 것인지, 아니면 '심사 보류 후 재시도 안내'로 둘 것인지는 전환율과 데이터 신뢰도 사이의 트레이드오프입니다. 이 결정은 캠코 심사 정책팀과 먼저 합의되어야 할 지점 아닌가요?

### 화면 4 — 부가정보 입력 `/signup/additional-info`

- **기능 요약**: API로 채울 수 없는 최소 항목만 수집 — 담당자 연락처, 정산계좌, (개인투자자의 경우) 투자자 적합성 확인 항목
- **User Flow**: 단일 페이지, 필드셋(Fieldset)으로 '담당자 정보'/'정산계좌 정보' 그룹핑 → 계좌 입력 시 금융결제원 실명조회 API로 Keyup 완료 후(Focusout) 즉시 예금주명 인라인 표시
- **CRUD**: Create/Update(담당자 정보, SettlementAccount)
- **정책**: 필수 항목이 소수이므로 KRDS 가이드에 따라 "선택 입력 항목만 [선택] 표시"하는 방식 채택(전체 항목 대비 필수 비중이 높으므로)

### 화면 5 — 최종 확인 및 제출 `/signup/confirm`

- **기능 요약**: KRDS 신청 패턴의 '확인/확정' 단계 — 제출 전 전체 데이터 리캡
- **User Flow**: 자동조회 정보(읽기전용) + 직접입력 정보(수정 가능, "수정" 링크로 화면4 복귀) 구분 노출 → 제출 버튼(Primary, 우측 하단) / 임시저장 버튼(Secondary)
- **CRUD**: Update(세션 → 정식 신청 레코드로 전환), 제출 즉시 버튼 비활성화(중복 제출 방지) + 스피너
- **정책**: 제출 확정은 KRDS '확인' 패턴 적용 대상 — 되돌릴 수 없는 행위이므로 별도 확인 모달("제출 후에는 대표자 인증 정보 재변경이 어렵습니다. 계속하시겠습니까?")

### 화면 6 — 가입/심사 결과 확인 `/signup/result`, `/mypage/application-status`

- **기능 요약**: 단계 표시기(Step Indicator)로 접수 → 자동검증 → (보완요청 있을 시) → 승인 상태를 시각화
- **User Flow**: 결과 목록(진행 상태별) → 상세 클릭 시 반려/보완 사유 인라인 노출
- **CRUD**: Read(ApplicationStatus 폴링 또는 웹훅 기반 갱신)
- **정책**: 보완요청 상태일 경우 해당 화면(3 또는 4)으로 딥링크하여 전체 Flow 재입력 방지

## 5. UI/UX 디자인 가이드라인 (KRDS 준수)

### 5-1. 전체 레이아웃 방식
- **단계형 입력폼(Step Form)** 채택 — KRDS 입력폼 패턴 중 '단계별 데이터 입력' 유형에 해당. 상단 고정 **단계 표시기(Step Indicator)** 로 0~6 진행률 노출(모바일에서는 축약형 "3/6"으로 표시)
- 각 단계 콘텐츠는 **단일 열(Single column) 수직 정렬**을 기본으로 하되, 정산계좌 은행명+계좌번호처럼 의미상 결합된 항목만 한 행에 수평 배치
- 데스크톱: 콘텐츠 영역 최대 720px 폭 중앙 정렬(2단 분할 대신 단일 포커스 유지 — 신청형 서비스는 좌우 분할보다 몰입형 단일 흐름이 이탈률에 유리) / 반응형: 360px 이하에서도 버튼 터치영역 44px 이상 확보

### 5-2. 액션 버튼 배치
- KRDS 가이드에 따라 제출/다음 단계 버튼은 **입력폼 우측 하단**, 임시저장·이전 버튼은 그 왼쪽에 순차 배치
- 필수 항목 미충족 시 제출 버튼은 **비활성화 상태**로 노출(직관적 인지 유도) + 중복 클릭 방지를 위한 제출 후 즉시 비활성화 처리

### 5-3. 공통 컴포넌트 도출 (프론트엔드 구현 단위)

| 컴포넌트명 | 용도 | 비고 |
|---|---|---|
| `StepIndicator` | 0~6단계 진행 상태 표시 | 데스크톱: 라벨형 / 모바일: 숫자 축약형 |
| `BizNoInput` | 사업자등록번호 입력(자동 하이픈, Keyup 검증) | 국세청 API 연동 |
| `AuthStatusBadge` | 계속사업자/휴업/폐업 상태 배지 | 색상 기반 상태 구분(배지 컴포넌트) |
| `ConsentAccordionList` | 동의 항목 리스트(일괄+개별) | KRDS 동의 패턴 구조 그대로 구현 |
| `ReadonlyDataCard` | 행정정보 자동조회 결과 카드 | 원문보기 모달 트리거 포함 |
| `DocumentPreviewModal` | 등기부등본/사업자등록증명원 원문 PDF 프리뷰 | 컴포넌트 수 5개 이내 원칙(모달 내 콘텐츠 최소화) |
| `AccountVerifyField` | 계좌 입력 + 실명조회 인라인 결과 | Focusout 검증 |
| `InlineErrorMessage` | 필드 단위 오류 메시지 | 서버측 검증 실패 시 해당 필드로 포커스 강제 이동 |
| `FormActionBar` | 다음/이전/임시저장 버튼 그룹 | 우측 정렬 고정 |
| `ApplicationStatusTimeline` | 심사 진행 상태 타임라인 | 화면6 전용, 폴링 기반 갱신 |

> **구현 가능성 코멘트**: `ReadonlyDataCard`와 `AuthStatusBadge`는 재사용 빈도가 높아 디자인 시스템 레벨의 공통 컴포넌트로 승격할 가치가 있습니다. 반면 계좌 실명조회처럼 외부 API 응답 지연(금융결제원 특성상 300ms~1.5s 편차)이 있는 컴포넌트는 스켈레톤/스피너 상태를 컴포넌트 자체 내장 상태(state)로 설계해야 향후 다른 신청 서비스(대출·보증)에도 그대로 재사용 가능합니다.
