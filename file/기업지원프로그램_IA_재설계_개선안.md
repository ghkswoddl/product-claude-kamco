# 캠코 온기업(ON-KIUP) 기업지원프로그램 개선안
## 전체 IA 재설계 — 신청자(법인/개인사업자) 중심 설계

> 범위: ① 지원사업 탐색·매칭 ② 신청 후 진행상황·이력 관리(마이페이지) ③ 기관 내부 운영 관리 화면을 아우르는 전체 IA
> 설계 기준: 신청자(법인/개인사업자) 중심, KRDS 목록탐색(global_04)·필터링정렬(global_10)·신청(service_04_01)·상세정보확인(global_06) 패턴 준수
> 전제: 직전 논의한 마이데이터·행정망 연계 회원가입 PRD의 산출물(진위확인된 기업 프로필 데이터)을 그대로 재사용하는 것을 전제로 설계

---

## 0. Why — 이 개선안이 필요한 이유

현재 구조의 가장 큰 문제는 "지원프로그램이 게시판처럼 나열되어 있고, 신청자가 본인에게 맞는 프로그램을 스스로 찾아야 한다"는 데 있습니다. 이는 두 가지 손실을 만듭니다.

- **발견 손실(Discovery Loss)**: 자격 요건에 맞는 프로그램이 존재해도, 신청자가 게시판을 끝까지 훑지 않으면 존재 자체를 모릅니다. 공공기관 서비스 특성상 이는 '전환율' 문제가 아니라 **정책 도달률(Reach) 손실**이라는 관점에서 보고되어야 합니다.
- **반복 입력 손실**: 프로그램마다 개별 신청서를 작성하며 이미 온기업이 보유한 기업정보(자본금, 업종, 매출 등)를 매번 다시 입력하게 됩니다. 이는 회원가입 단계에서 이미 해결한 문제를 신청 단계에서 다시 만드는 구조적 모순입니다.

> **비즈니스 근거**: 캠코의 지원사업 집행률(예산 대비 실집행) 저하 원인 중 상당 부분은 '몰라서 못 신청'입니다. 신청자 유입 자체가 아니라 **자격에 맞는 신청자와 프로그램의 매칭률**을 KPI로 설계해야 하는 이유입니다.

> **글로벌/국내 벤치마킹**: 기업마당(bizinfo.go.kr)은 업종·지역·기업형태 기반 맞춤 정보 알림 기능을 제공하지만 알림이 이메일/문자 중심이라 서비스 내 탐색 경험과 분리되어 있습니다. 반면 GOV.UK의 "Find support for your business" 서비스는 몇 개의 질문(업종/지역/직원 수)에 답하면 적합한 지원 프로그램만 좁혀 보여주는 위저드형 매칭을 제공합니다. 온기업은 이미 회원가입 시점에 진위확인된 기업 데이터를 보유하므로, GOV.UK보다 한 단계 더 나아가 **질문 없이 자동 매칭**이 가능한 구조적 우위가 있습니다.

> **디렉터 관점 질문 1**: 매칭 알고리즘을 '자격요건 필터링(Rule-based, 100% 정합성)'으로만 설계할 것인지, 아니면 '유사 프로필 기반 추천(추가 발견 유도)'까지 포함할 것인지는 이번 IA의 신뢰도-발견성 트레이드오프를 결정하는 핵심 지점입니다. 공공기관 특성상 부적격 추천 노출은 민원으로 이어질 수 있어 신중한 판단이 필요합니다.

## 1. 서비스 개요 및 목적

| 항목 | 내용 |
|---|---|
| 개선 대상 | 기업지원프로그램 전체 여정 — 탐색/매칭 → 신청 → 진행상황 관리 → (기관측) 등록/심사 운영 |
| 핵심 목표 | ① 진위확인된 회원 프로필 기반 **자동 자격 매칭** ② 프로그램 간 신청정보 재사용으로 반복 입력 제거 ③ 신청 후 전 과정을 하나의 타임라인에서 추적 |

## 2. 타깃 유저 및 핵심 가치 (유저 시나리오)

### 2-1. 유저 정의 및 사용 환경
- **주 사용자**: 법인/개인사업자 대표 또는 재무·경영지원 담당자. 데스크톱에서 여러 탭을 열어 프로그램을 비교하는 행태가 많고(재무제표 등 참고자료 병행 확인), 모바일에서는 마감 임박 알림 확인 후 상세 재검토 목적의 짧은 세션이 많습니다.
- **부차 고려**: IA는 신청자 중심으로 설계하되, 운영 담당자가 프로그램을 등록·수정하는 화면의 데이터 구조가 신청자 화면에 그대로 노출되는 필드(자격요건, 마감일, 지원한도)와 1:1로 매핑되어야 재설계 효과가 있습니다. 운영 화면을 별도로 재설계하지 않으면, 신청자 화면만 아무리 다듬어도 '자격요건 텍스트가 자유서술이라 자동매칭이 불가능한' 근본 문제가 남습니다.

### 2-2. 핵심 유저 시나리오
> "이미 온기업 회원인 제조업 소상공인 대표가, 로그인하자마자 '나에게 해당하는 지원사업이 있는지' 알고 싶어한다."

1. 로그인 직후 메인 화면에서 "회원님이 신청 가능한 프로그램 N건"을 즉시 확인한다(별도 탐색 없이).
2. 매칭된 프로그램 상세에서 자격요건 중 어떤 항목이 왜 충족되었는지(자본금 기준 충족, 업종 코드 일치 등) 근거를 확인한다.
3. 신청 버튼을 누르면 회원 프로필 데이터가 자동으로 채워진 신청서가 열리고, 프로그램 고유 항목만 추가 입력한다.
4. 마이페이지에서 여러 프로그램의 진행 상태(접수/심사중/승인/반려)를 하나의 목록에서 한눈에 확인한다.

## 3. 핵심 정보 구조(IA) 및 메뉴 트리

### 3-1. GNB/LNB 구조
```
GNB: 온기업 홈 / 기업지원프로그램 / 마이페이지 / 고객센터
└ 기업지원프로그램 (LNB)
   ├ 맞춤 매칭 (로그인 시 기본 진입 – 신청자별 개인화 화면)
   ├ 전체 프로그램 탐색 (비로그인/전체 목록, 필터링·정렬)
   ├ 분야별 보기 (자금·보증 / 컨설팅·경영지원 / 투자연계 / 판로·수출)
   └ 마감임박
└ 마이페이지 > 신청 이력 (LNB)
   ├ 진행중인 신청
   ├ 완료/종료된 신청
   └ 관심 프로그램(찜)

[기관 내부 – 별도 운영자 도메인, 참고용 IA]
└ 프로그램 관리자 콘솔
   ├ 프로그램 등록/수정 (자격요건을 구조화 필드로 입력 — 자유서술 지양)
   ├ 신청 접수 및 심사
   └ 집행 현황 대시보드
```

> **구조적 판단**: '맞춤 매칭'을 LNB 최상단 기본 진입점으로 배치한 것은, KRDS 목록탐색 패턴의 "중요한 항목은 좌측 상단/목록 상단에 배치한다" 원칙을 개인화 우선순위에 그대로 적용한 것입니다. '전체 탐색'은 그다음 우선순위로, 매칭에서 걸러지지 않은 프로그램을 스스로 찾고 싶은 사용자를 위한 대안 경로로 남겨둡니다.

### 3-2. 주요 데이터 개체 및 관계 구조
```
[지원프로그램(Program)] 1 --- N [자격요건(EligibilityRule: 필드형 – 업종코드/자본금범위/기업규모/지역)]
[회원(Member)] N --- N [프로그램매칭이력(MatchLog: 매칭점수, 충족/미충족 근거)]
[회원(Member)] 1 --- N [신청(Application: 프로그램FK, 상태, 제출일)]
[신청(Application)] 1 --- N [신청서스냅샷(ApplicationSnapshot: 회원프로필에서 복사된 시점 데이터)]
[회원(Member)] N --- N [관심프로그램(Bookmark)]
```

- **핵심 설계 판단**: `EligibilityRule`을 자유서술 텍스트가 아닌 **구조화 필드(업종코드, 자본금 범위, 기업규모 구분, 지역 코드)**로 관리하는 것이 이번 재설계의 전제 조건입니다. 이 부분이 해결되지 않으면 신청자 화면의 '자동 매칭'은 UI만 그럴듯한 하드코딩 룰 몇 개로 그치게 됩니다. → 운영 콘솔의 프로그램 등록 화면 개선이 신청자 경험 개선의 **선행 종속 작업**임을 명확히 해야 합니다.

> **디렉터 관점 질문 2**: 지금 등록된 기존 프로그램들의 자격요건이 대부분 자유서술 텍스트(공고문 PDF 첨부 방식)로 되어 있다면, 전수 구조화 작업(데이터 마이그레이션)의 공수를 먼저 산정해야 합니다. 이 개선안의 1차 릴리스 범위를 '신규 등록 프로그램부터 구조화'로 한정할지, '기존 프로그램 전체 소급 적용'까지 포함할지는 개발 착수 전 반드시 결정되어야 할 지점 아닌가요?

## 4. 상세 기능 명세 (화면별 요구사항 및 정책)

### 화면 1 — 맞춤 매칭 `/programs/matched`

- **기능 요약**: 로그인 회원의 프로필 데이터를 기준으로 자격 충족 프로그램만 필터링해 노출. 로그인 직후 랜딩 후보 화면.
- **User Flow**: 로그인 → 매칭 계산(서버측, 실시간 또는 사전 배치) → 카드형 목록(구조화 목록 컴포넌트) → 카드 클릭 시 상세 → "왜 이 프로그램이 매칭되었나요?" 디스클로저로 근거 항목 펼쳐보기
- **CRUD**: Read(MatchLog 조회 또는 실시간 계산), 조회 시점 캐시(TTL 1일, 회원 프로필/프로그램 변경 시 무효화)
- **데이터 상태/예외**: 매칭 결과 0건일 경우 빈 상태(Empty state) — "관심 분야를 설정하면 새 프로그램 등록 시 알림을 받을 수 있습니다" 형태의 대안 액션 제시(막다른 화면 지양)
- **정책**: 매칭 근거는 반드시 항목 단위로 명시(예: "자본금 3억 이하 요건 충족", "제조업 업종코드 일치") — 근거 없는 '추천'은 공공서비스 신뢰도 관점에서 지양

### 화면 2 — 전체 프로그램 탐색 `/programs/list`

- **기능 요약**: 비로그인 사용자도 접근 가능한 전체 목록. 필터/정렬 기반 탐색.
- **User Flow**: 목록 상단 정렬 컨트롤(마감임박순/최신등록순/지원한도순 – 수평 배치) + 좌측 필터 패널(분야/지역/기업규모/지원형태 – 수직 배치) → 필터 적용 즉시 결과 갱신(데이터 규모 고려 시 즉시 반영, 대량일 경우 "적용" 버튼 명시)
- **CRUD**: Read(Program 목록, 페이지네이션 또는 더보기 – 항목 수 20개 초과 시 페이지네이션 적용)
- **정책**: 검색 결과 수를 목록 상단에 명시. 필터가 여러 개 적용된 경우 적용된 필터를 태그(Tag) 컴포넌트로 목록 상단에 노출하고 개별 해제 가능하게 구성

### 화면 3 — 프로그램 상세 `/programs/{id}`

- **기능 요약**: 자격요건, 지원내용, 신청기간, 제출서류를 KRDS 상세정보확인 패턴에 따라 구조화 노출
- **User Flow**: 핵심 요약(지원한도/마감일/자격요건 배지) 상단 고정 → 상세 본문 → 첨부파일(공고문 원문) → 하단 고정 신청 버튼(Sticky, 스크롤 중에도 노출)
- **CRUD**: Read(Program 상세), 로그인 회원인 경우 자격 충족 여부를 상세 화면 상단에 배지로 즉시 표시(비충족 시 신청 버튼 비활성화 + 사유 명시)
- **예외 처리**: 마감된 프로그램은 신청 버튼 대신 "마감되었습니다" 상태 + 유사 진행중 프로그램 추천 링크로 이탈 방지

### 화면 4 — 프로그램별 신청 `/programs/{id}/apply`

- **기능 요약**: 회원가입 시 확보한 회원 프로필(ApplicationSnapshot)을 자동 반영하고, 프로그램 고유 항목만 추가 입력받는 경량 신청폼
- **User Flow**: 자동 반영 항목(읽기전용 카드, 이전 PRD의 `ReadonlyDataCard` 재사용) → 프로그램 고유 입력 항목(필드셋으로 그룹핑) → 최종 확인 → 제출
- **CRUD**: Create(Application, ApplicationSnapshot – 신청 시점 프로필 스냅샷을 별도 저장하여 이후 회원정보가 바뀌어도 신청 당시 근거 유지)
- **정책**: KRDS 입력폼 가이드의 "단계가 있는 입력폼에서 반복 입력 정보를 자동 입력" 원칙을 프로그램 간에도 확장 적용 — 이미 다른 프로그램에 신청하며 입력한 고유 항목(예: 사업계획 요약)이 있다면 "이전 입력값 불러오기" 옵션 제공

### 화면 5 — 마이페이지 신청 이력 `/mypage/applications`

- **기능 요약**: 여러 프로그램에 걸친 신청 현황을 상태별로 통합 관리
- **User Flow**: 상태 필터 탭(진행중/완료/반려) → 목록(구조화 목록, 프로그램명·신청일·현재상태·마감일 병기) → 개별 항목 클릭 시 단계 표시기 기반 상세 진행상황
- **CRUD**: Read(Application 목록, 상태별 필터링) / Update(반려 시 보완 제출 – 화면4로 딥링크, 스냅샷 위에 수정분만 반영)
- **정책**: 마감 임박(3일 이내) 진행중 항목은 목록 상단 고정 + 강조 배지로 시각적 우선순위 부여

### 화면 6 — 관심 프로그램(찜) `/mypage/bookmarks`

- **기능 요약**: 현재 자격 미충족이나 향후 조건 변경 시 신청 가능한 프로그램을 저장. 재방문 유도 채널.
- **CRUD**: Create/Delete(Bookmark) / Read(찜 목록, 마감 임박 시 알림 트리거 대상)

### 화면 7(운영) — 프로그램 등록/수정 `/admin/programs/new` — 참고 명세

- **기능 요약**: 자격요건을 자유서술이 아닌 **구조화 입력폼**으로 등록하도록 강제. 이 화면의 데이터 구조가 화면1의 매칭 로직 정확도를 결정.
- **User Flow**: 기본정보(프로그램명/공고문 첨부) → 자격요건(업종코드 다중선택 셀렉트, 자본금 범위 – 최소/최대 숫자입력, 기업규모 라디오, 지역 체크박스) → 지원내용 → 신청기간(날짜입력 컴포넌트, 날짜 선택기 대신 직접입력+형식안내) → 미리보기(신청자 화면 기준 프리뷰 제공) → 등록
- **정책**: "미리보기" 단계를 필수 통과 지점으로 두어, 운영 담당자가 자신이 입력한 구조화 데이터가 신청자 화면에 실제로 어떻게 매칭·노출되는지 등록 전에 확인하게 함 — 운영자와 신청자 화면 간 데이터 정합성 오류를 사전 차단하는 장치

## 5. UI/UX 디자인 가이드라인 (KRDS 준수)

### 5-1. 레이아웃 방식
- **목록형 화면(화면1,2,5,6)**: KRDS 구조화 목록(Structured list) 패턴 — 중요 정보(마감일, 매칭 배지)는 좌측 상단 우선 배치, 항목 간 충분한 여백과 구분선 확보
- **필터+목록 화면(화면2)**: 데스크톱은 좌측 필터 패널 고정 + 우측 목록 2단 분할, 반응형은 필터를 상단 "필터" 버튼 클릭 시 바텀시트/모달로 전환(모바일에서 좌측 고정 패널은 콘텐츠 영역을 과도하게 축소시키므로 지양)
- **상세 화면(화면3)**: 신청 버튼은 Sticky 하단 고정 — 상세 정보가 길어질 수 있는 공공 공고문 특성상, 스크롤 중에도 핵심 액션 접근성 유지가 이탈 방지에 직접적 영향

### 5-2. 공통 컴포넌트 도출 (프론트엔드 구현 단위)

| 컴포넌트명 | 용도 | 비고 |
|---|---|---|
| `MatchScoreBadge` | 매칭 여부/충족 근거 배지 | 클릭 시 근거 디스클로저 확장 |
| `ProgramCard` | 목록형 프로그램 카드(매칭/전체 탐색 공용) | 마감임박 시 강조 스타일 분기 |
| `FilterPanel` | 분야/지역/기업규모/지원형태 필터 | 데스크톱 고정형 / 모바일 바텀시트형 반응형 분기 |
| `SortBar` | 정렬 컨트롤(수평 배치) | 필터와 시각적으로 군집화 배치(KRDS 가이드) |
| `AppliedFilterTags` | 적용된 필터 태그 목록 + 개별 해제 | Tag 컴포넌트 재사용 |
| `EligibilityRuleBuilder` | (운영자용) 자격요건 구조화 입력 | 자유서술 입력 차단, 셀렉트/범위입력 강제 |
| `ProgramPreviewPane` | (운영자용) 등록 전 신청자 화면 미리보기 | 등록-노출 정합성 검증용 |
| `ApplicationTimeline` | 신청 진행상태 타임라인 | 회원가입 PRD의 `ApplicationStatusTimeline` 확장 재사용 |
| `StickyApplyBar` | 상세 화면 하단 고정 신청 버튼 | 스크롤 무관 고정, 마감/자격미충족 상태 분기 노출 |

> **구현 가능성 코멘트**: `ProgramCard`와 `ApplicationTimeline`은 회원가입 PRD에서 도출한 `ReadonlyDataCard`, `ApplicationStatusTimeline`과 데이터 셰이프가 유사합니다. 두 PRD를 별개 스프린트로 진행하더라도, 디자인 시스템 레벨에서는 "상태 기반 카드"와 "단계 기반 타임라인"이라는 두 개의 상위 패턴으로 통합 설계하면 두 기능 간 컴포넌트 재사용률을 높일 수 있습니다.

## 다음 논의가 필요한 지점

1. 기존 등록 프로그램의 자격요건 데이터 구조화(마이그레이션) 공수 산정 — 이것이 선행되지 않으면 화면1(맞춤 매칭)의 정확도는 보장되지 않습니다.
2. 매칭 로직의 성격을 '자격요건 100% 충족 필터링'으로 한정할지, '유사 프로필 기반 추천'까지 확장할지 — 부적격 추천 노출 시 민원 리스크와 발견성 향상 사이의 정책적 결정
3. 신청서 재사용(이전 프로그램 입력값 불러오기) 시, 프로그램별로 요구 서식이 다른 경우의 매핑 규칙을 어디까지 자동화할지 — 완전 자동 매핑이 어려운 항목은 신청자가 검토·수정하는 반자동 구조로 남겨야 할 가능성
